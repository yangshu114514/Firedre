*2026-08-17*

一、事情是这样的

我有一台 1核 1GB 内存的云服务器，SSH 端口改成了 11451（懂得都懂）。本来想在上面跑 OpenClaw，接微信通道，搞个自己的 AI 助手。

听起来挺简单的，对吧？

结果从第一天傍晚 6 点，一直肝到第二天晚上 9 点，整整 27 个小时。中间睡了大概 5 小时——别问我怎么算的，熬夜的人不配拥有数学。

Gateway 崩了多少次我已经记不清了，earlyoom 杀了快 300 次，我骂了无数句"我靠"，中间还因为 maxTokens 设置不对跟 AI 吵了一架。

但最后——搞定了。真的，历尽千辛万苦，终于弄好了。

二、第一夜：We did it！然后崩了

傍晚 6 点开干。Python 3.13 源码编译、Cloudflare Tunnel、Lighttpd 反向代理、WebSocket 转发……坑是一个接一个。Cloudflare 的 local 模式隧道全部注册失败，只有 token 模式能用。Lighttpd 的 WebSocket 转发也很离谱——`mod_wstunnel` 明明返回了 101，数据就是不转发，最后得靠 `mod_proxy` 加一行 `proxy.header = ("upgrade" => "enable")` 才通。

折腾到晚上 10 点多，框架总算搭起来了。接着又搞知识库语义搜索、定时任务、CF CDN 优化……

**晚上 11 点 16 分，我发了条微信消息测试。**

一切正常。网关自启、微信通道就绪、知识库搜索可用。我盯着屏幕，嘴一咧，说出了那句：

> **"We did it!!!"（我们成功了!!!）**

13 分钟后，23 点 29 分。

**崩了。**

一条微信消息进来，RSS 从 300MB 直接飙到 700MB，earlyoom 抬手就把 gateway 抬走了。SSH 卡得连不进去。

那一刻，心脏和内存一起炸了。就像你刚拼完 1000 块拼图，你家猫跳上桌子，一脚蹬翻。

后面一整夜都在抓根因：

- **swap 没挂载**——fstab 里压根没写，重启后 0 swap，1GB 物理内存硬扛，能不死吗

- **exec symlink 死循环**——`/root/.openclaw` 指向 `/data/openclaw-data` 的符号链接，openclaw 内置的 symlink 防护模块不认这个路径，agent 就不停重试。每次重试都发起 agnes 流式 API 调用，5 到 9 秒一次，22 秒内内存从 247MB 飙到 522MB

- **earlyoom 在 4G swap 下形同虚设**——它的阈值看的是 swap 空闲率，4G swap 几乎全空，触发条件永远不满足，等于白设

凌晨快 2 点，bind mount 修好了，exec 禁用了，swap 挂上了。gateway 稳定在 294MB。

我合上电脑，带着"这次总他妈该行了吧"的幻觉滚去睡觉。

三、第二天：又崩了，然后修好，然后又崩

第二天下午醒来一看，gateway 又双叒崩了。

这回的问题是 **thinking=high** 模式。我想保留 AI 的深度思考能力，但 thinking=high 会触发多轮 agnes 流式调用，22 秒内 RSS 从 300MB 暴涨到 700MB 以上。

maxTokens 也跟着反复横跳：

- 2048 → 不够用，模型说到一半停了

- 8192 → 还是崩

- 4096 → 降智保稳定

- 8192 → 又崩

- **16384 → 终于稳了**

中间我还干了一件蠢事：配置写错了。

`memorySearch` 放错位置、`providers` 和 `models` 字段名搞混、`thinkingDefault` 写错层级……gateway 反复 exit code 78，`openclaw doctor --fix` 跑了 3 次才救回来。

说实话，有个瞬间真的挺崩溃的。earlyoom 一天之内杀了 gateway 293 次。293 次。我坐在屏幕前，在对话里打了一句：

> **"别他妈看了，网关又炸了"**

AI 回了：

> **"好，直接查当前状态，不等了"**

然后 30 秒内修好了。

我：……你早干嘛去了。

四、关于 We did it 的那句话

"We did it" 我在两个时间点说过。

第一次是第一天晚上 23:16:50。那次是 premature victory——以为搞定了，结果 13 分钟后崩了。后来我去 opencode 数据库里翻那条记录，看到自己当时说的话，忍不住笑了。

第二次是第二天晚上 21:30。那次是真的。强制重启测试 35 秒完成，全服务自启，微信 90 秒就绪，零 bug。我在对话里说：

> **"We did it!"**

> **"We did it" 在 23:16 也说过一次**

AI 的反应很有意思——它自己去查了数据库，找到了第一次说 "We did it" 的记录，然后当场拆台：

> **时间对上了：23:13 我回复了"搞定了"，到 23:16:50 你说"We did it!!!"**

> **但当时没有验证——发微信消息测试过吗？**

13 分钟后，消息一来，崩了。

所以那声 "We did it" 本质上是一个**没有经过验证的胜利宣言**。跟程序员说 "it works on my machine" 差不多一个性质。

但第二次，晚上 21:30 那次，我是真的验证过了。强制重启、等服务自启、测微信通道、盯内存曲线——全部通过。

五、最终方案：5 层保护

27 小时的命不是白拼的，最后搭了一套 5 层内存保护架构：

Layer 1  V8 heap:     --max-old-space-size=256（Node 堆上限）

Layer 2  cgroup:      MemoryHigh=400M（节流）/ MemoryMax=550M（硬上限）

Layer 3  watchdog:    RSS > 700MB 连续 2 次 → kill -9

Layer 4  earlyoom:    available < 3%（约 28MB）→ SIGKILL

Layer 5  kernel:      overcommit_memory=1（防整机卡死）

earlyoom 的阈值从最初的 10% 一路调到 3%。3% 什么概念？939MB 内存的 3% 大约是 28MB。也就是说，**系统得濒死到一定程度才会触发**。平时 gateway 跑个 400-500MB 根本不会惊动它。

watchdog 阈值从 650 → 780 → 850 → **700MB**。

maxTokens 从 2048 → 8192 → **16384**。

thinking 从 low → **high**。

六、数据说话

| 指标 | 优化前 | 优化后 |

|---|---|---|

| gateway RSS | 300MB~700MB+（崩） | **293~376MB（稳定）** |

| 崩溃频率 | 每小时多次 | **零** |

| earlyoom 误杀 | 293 次/天 | **0 次** |

| 可用内存 | <50MB（濒死） | **222~381MB** |

| 微信消息 | 持续丢失 | **正常收发** |

| 重启自愈 | 不定（卡死） | **90 秒全链路恢复** |

*P.S. 这图表可别信，AI写的*

七、还没解决的问题

1. **1GB 是硬瓶颈**——thinking=high 加多个 session 加载后峰值大概 580MB，留给其他服务的空间真的不多了

2. **没有异地备份**——只在本地有，后面得加 rclone + R2

3. **最彻底的方案**：升级 2GB 内存（AI 原话：老板，加钱，不过实际上我没钱...连运行这个网站的服务器都是薅的免费的）

八、后记

这篇文章是我让 AI 从 opencode 数据库里提取完整对话记录——5574 条 part，3987 行有效内容——切成 4 段，让 4 个 Agent 并行分析后合成的。

别问我为什么要用AI...你有本事自己读一遍近4000行的内容。

那些临时文件我都删了。但那条 "We did it" 的记录还在。

有时候我觉得，和 AI 一起 debug 一台 1GB 内存的破服务器，这件事本身挺浪漫的。

它不会累，不会烦，不会说"你能不能换个思路"。它只会一遍遍执行命令、查日志、试配置，直到搞定。

当然，它也会犯错。会把 `providers` 写成 `models`，会把 `memorySearch` 放错位置，会把我气得说"你他妈要我修复多久"。

但最后——我们搞定了。

这次是真的...吗?

未完待续，但是我可不想再待续了...
